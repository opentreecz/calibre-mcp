# Development, CI, and releases

Use **Python 3**, preferably 3.14. The supported minimum is 3.10; the Docker
image and primary CI jobs use 3.14. Do not use a system `python` command that
resolves to Python 2.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m ruff check .
.venv/bin/python -m pytest --cov=calibre_mcp --cov-report=term-missing
docker compose config --quiet
docker build -t calibre-mcp:test .
docker run --rm -v "$PWD/tests:/tests:ro" --entrypoint python3 calibre-mcp:test /tests/container_smoke.py
```

On Windows, use `.venv\Scripts\python.exe` for virtual-environment commands.
The tests use a disposable mock, never your live library. Both MCP transports
are tested through the SDK/HTTP, in addition to direct tool tests. The mock
does not implement calibre's full query language or conversion engine; live
calibre compatibility still needs the optional `scripts/smoke.py` check.

## Workflows

| File | Purpose |
|---|---|
| `.github/workflows/lint.yml` | Ruff correctness checks and actionlint workflow validation |
| `.github/workflows/test.yml` | Python 3.10/3.14 × minimum/latest MCP 1.x, coverage and JUnit artifacts |
| `.github/workflows/docker.yml` | Build, HTTP container smoke test, amd64/arm64 build and optional GHCR push |
| `.github/workflows/release.yml` | On `main`: call all checks, create a release, explicitly call image publication |
| `.github/dependabot.yml` | Weekly grouped pip updates, Actions updates, Docker updates |

Pull requests run lint, tests and container builds without registry publishing.
Pushes to `main` run the same reusable checks through Release. Actions are
pinned to commit SHAs; Dependabot maintains those pins. Build artifacts and
coverage are available on each test run. No real-library credentials are needed.

## Automatic versioning

The first successful `main` pipeline releases **v0.1.0**. After that, commit
messages since the latest reachable semantic-version tag determine the bump:

- `fix:` / `perf:` → patch
- `feat:` → minor
- `feat!:` or a `BREAKING CHANGE:` footer → major (also before 1.0)
- `docs:`, `test:`, `ci:`, `chore:` alone → no versioned release

Use Conventional Commit PR titles when squash merging. GitHub generates release
notes. Release jobs serialize, and retries reuse an existing tag for the same
commit rather than bumping again. Tags/releases are created only after checks
pass. The publisher is explicitly called because events generated by
`GITHUB_TOKEN` do not normally trigger another workflow.

Images: `ghcr.io/opentreecz/calibre-mcp:sha-<full-commit>` on successful main
pipelines; `:0.1.0` and `:latest` on a release. `latest` means latest stable
release, not every main commit. A GitHub release can exist before its image
finishes publishing; check the Release run before pulling a new tag. Rerun failed
jobs to retry publishing.

## Repository setup

Enable GitHub Actions and allow the workflows to use `contents: write` and
`packages: write` through `GITHUB_TOKEN`. No personal token is needed by CI.
Make the GHCR package public after first publication for anonymous pulls;
otherwise users must authenticate with an account that can read it.

Configure branch protection for the PR lint, test matrix and Docker checks.
Auto-merge follows repository rules; enabling auto-merge does not bypass required
reviews or checks. Dependabot opens PRs; it does not automatically merge them.

To trigger a retry manually, run Release on `main` from Actions. Dispatching
the standalone Docker workflow validates builds without publishing.
